# Phase 0 获客测试手册（2026-11-05）

> **目的**：用最低成本验证一件事——**有没有人愿意为「行程体检」停下来找你**。
> 这是整个「体检获客 → 行中值班」漏斗的止损闸门：**10 个免费名额一周内约不满，
> 后面两轮都不做**（见 [NEXT_STEPS.md](NEXT_STEPS.md) 的止损表）。
>
> 本手册只覆盖 Phase 0：**不写产品代码、不改部署**。交付是人工的（我/你亲手出报告），
> 因为要验证的是需求，不是自动化程度。

---

## 1. 测试设计（为什么这样设计）

| 设计选择             | 理由                                                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **限 10 份**         | 人为稀缺 = 可测量的响应速度。不限量就无法判断「约满」；10 份是一个人能手工交付的量                                   |
| **免费**             | 此时在验证需求，不是在验证付费。付费意愿放到第 11 份起测（¥19.9）                                                    |
| **用对方自己的行程** | 关键对照：我们**不生成**行程，只核验对方已有的一份。这直接避开「生成已商品化」的红海，也验证「复核是刚需」这个假设   |
| **不承诺能改好**     | 只交付判定 + 证据 + 可复算凭据。改不改、怎么改由对方决定——这与产品的「体检而非隐瞒」原则一致，也不能在交付时过度承诺 |
| **一个人工交付**     | 目标就是看「拿到报告的人会不会真的用」。自动化是 Phase 1 之后的事                                                    |

**要回答的问题（按优先级）**：

1. 10 份名额多久约满？（< 3 天 = 强信号；> 7 天 = 需求不成立）
2. 拿到报告的人，**当天**有没有导入日历 / 打开分享链接？（Phase 1 的真信号）
3. 有没有人说「这一条我自己没想到」？（价值浓度）
4. 有没有人主动问「能不能帮我改」？（从核验走向值班的桥）

### 2.3 私信回复模板（有人来问时）

> 可以，把行程发我（文字/截图都行，几点到几点、去哪、待多久，越全越准）。
> 我出一份体检报告给你，大概今天内好。
>
> 两种查法，你选：

> ② **全**：连地点真实性、营业时间一起核（要走一遍生成，慢几分钟，

>
> 提醒一下：我只出「哪有问题、为什么」，不替你改行程；报告是时点结论，

## 3. 交付 SOP（每份约 15–30 分钟）

### 3.1 输入整理

用户发来的通常是文字或截图。整理成 Trip Check 开放文档（格式见
[TRIP-CHECK-STANDARD.md](../../TRIP-CHECK-STANDARD.md) §3，机器契约 `GET /api/verify/schema`）：

1. 逐点位抽出：`name` / `time`（`HH:MM-HH:MM`）/ `durationMin` / `costCny` / `type`；
2. **没有的信息不要编**：缺 `durationMin` 就跳过节奏判定（TC-C105 会如实报「信息不足」），
   缺路段就报「无法判断通勤」（TC-C104）——这正是产品的三态原则，交付时也是卖点；
3. `date` 尽量填（有日期才能判营业时间/闭馆日）；没有就留空，不猜周几；
4. `verification` 字段**不要伪造**：没查过就留空或 `not_checked`，让事实轴如实显示
   「未核验」。可以只做结构轴体检（也能出结论），并在交付时说明这一点。

### 3.2 跑体检（两种模式，先看清边界再选）

**模式 A · 结构体检（默认，~5 分钟）**——只查文档本身，不查真实世界。

`POST /api/verify` 是**无状态纯引擎**：不调高德、不查 POI。所以它能判的是
时间轴/节奏/预算/绕路/重复，**不能**判「地点是否真实、那天开不开门」——除非文档自己
声明了 `verification`。外部行程没声明，事实轴就会如实显示「未核验」。
这不是缺陷，是标准的三态设计（`未核验 ≠ 不存在`），交付时反而要当成卖点讲。

```bash
# 注意：请求体必须是 {"document": {...}} 包装，不能把文档字段放顶层！
# （顶层直接放会报 "document 与 shareId 必须且只能提供一个"——实测踩过）
jq -n --slurpfile d doc.json '{document: $d[0]}' > req.json

curl -s -X POST http://localhost:3000/api/verify \
  -H 'Content-Type: application/json' \
  --data-binary @req.json | jq
```

或把同一份 `req.json` 粘到 `/verify` 体验台。报告含两轴结论、规则级问题、凭据 ID。

**模式 B · 含事实核验（对方明确要求时，~5–10 分钟）**——会重排，要提前说清。

把对方行程原文走我们自己的流水线：`POST /api/plan/extract`（原文→条件）→
`POST /api/plan`（生成，v5「事实先行」会在这时用高德验真 POI/营业时间/通勤）→
报告走 `/p/<shareId>/check`。

- 前提：`.env` 的 `AMAP_WEB_SERVICE_KEY` 有效（`/api/health` 的 `amapMode` 为 `live`）；
  MOCK 模式下**不能**说「已核验」。
- 代价：出来的是**按对方行程重排后的版本**，不是原文逐字核对——这一点必须在交付时讲明。
- 已验证证据（不必重跑）：`npm run verify:amap` 全绿；`EVAL_CASES=3 npm run eval:cases`
  实测 3/3 成功、POI 验真 100%（51/51）（见 [NEXT_STEPS.md](NEXT_STEPS.md)）。

### 3.3 交付物（三选一或全给）

| 形态           | 怎么给                                     | 适用             |
| -------------- | ------------------------------------------ | ---------------- |
| **纯文本报告** | 报告页「复制纯文本」，粘到微信             | 最快，覆盖最多人 |
| **报告页链接** | 把 JSON 贴到 `/verify` 出报告后截图/发链接 | 对方想自己看细节 |
| **竖版海报**   | `/p/<id>/check/poster`                     | 对方想转发       |

### 3.4 交付话术（跟着报告走，别夸大）

> 报告出来了，先说结论：**结构自洽性 X 级，事实核验覆盖率 Y%**——这是两件事，分开看。
>
> 阻断问题 N 条（按文档数据走不通）：
>
> - [规则号] 具体问题
>   建议：……
>
> 事实这一轴，我查了哪些、哪些没查，报告里都列了。没查的不代表没问题，代表不知道。
> （模式 A 下这一轴就是「未核验」——要明说，别让对方以为地点和营业时间已经查过。）
>
> 结论可复算：同一份文档 + 同一套规则版本，谁跑出来的凭据 ID 都一样。
> 但它是**时点结论**——营业时间以你出发那天为准，不是承诺。

## 5. 判定与止损

| 观察                       | 阈值             | 动作                                                       |
| -------------------------- | ---------------- | ---------------------------------------------------------- |
| 10 份名额约满速度          | **> 7 天约不满** | **停止 Phase 1/2**，回到 B 端问价（PRODUCT-REVOLUTION S2） |
| 约满速度 < 3 天            | 强需求信号       | 立刻加名额，进入 Phase 1                                   |
| 拿到报告当天导入日历的比例 | **< 20%**        | 「值班」是伪需求，Phase 1 只做体检获客，不做日历           |
| ≥ 50% 导入日历             | 强信号           | Phase 2 提前做「异常一等入口」                             |
| 有人主动问「能不能帮我改」 | 有               | 这是 Phase 2 的优先级排序依据                              |
| 连续 20 个用户零付费       | 达到             | 回到 B 端问价                                              |

## 6. 已知边界（交付时必须说，不能说成「已核验」）

- **MOCK 模式 / 未声明来源的文档不会被说成「真实世界核验」**；示例营业时间是示意数据；
- 凭据**保证可复算，不是数字签名**；
- 报告是**时点结论**，营业时间以出发当天实际为准；
- 只判不改：不替用户做换点/删点/改日期的取舍（确定性修复是另一条产品线，Phase 2 再谈）。
