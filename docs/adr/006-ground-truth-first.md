# ADR-006: 事实先行（生成前给事实，而不是生成后查事实）

## 状态

已接受（2026-10）

## 背景

产品最初的生成链路是「先编后验」：

```
LLM 盲写 POI 名 → 高德逐个验真 → 体检抓闭馆日/绕路/时间接不上 → 用户一键修复
```

prompt 里写着「POI 名称（必须真实存在）」——但模型手上**没有任何真实数据**，
它只能靠记忆编名字、靠常识排时间。于是：

- 「周一闭馆的苏州博物馆」会被排到周一（模型不知道闭馆规则）；
- 两站之间要开 22 分钟，模型按「都在老城区」排成 10:15 → 10:30；
- 编造的名字在验真阶段变成「未在高德检索到」预警。

也就是说，产品最值钱的能力（真实世界事实）**全部用在了生成之后**。
体检成了生产线上的质检员，而不是安全网——它能发现问题，但不能避免问题。

## 决策

把事实层**前置**到生成之前：

```
高德候选检索 → 事实清单（真实存在 + 营业时间 + 闭馆日 + 评分 + 人均）
             → 注入 prompt → 模型在真实事实上排行程 → 体检退化为兜底
```

具体三条：

1. **新增 `lib/grounding.ts`**：检索候选 → 按高德 `type` 归类（景点/餐饮）→
   用 `checkDayAvailability` 逐个行程日判定闭馆 → 生成「素材清单」文本块。
2. **新增 `lib/amap.ts` 的 `searchPois`**：与 `lookupPoi` 并存的第二入口。
   `lookupPoi` 问「这个名字存在吗」（取 top1，生成后用）；
   `searchPois` 问「有哪些可选」（取列表，生成前用）。
3. **新增 `lib/poi-hours.ts` 的 `checkDayAvailability`**：回答「这一天它开不开门」，
   与 `checkOpenHours`（回答「我 10:30 到，它开不开门」）分工明确，两者不可混用。

## 理由

- **闭馆冲突在源头消失**：闭馆日进了 prompt，模型就不会把博物馆排到周一。
  体检里的「闭馆」预警从「事后抓」变成「事后确认」——它应该几乎不响。
- **POI 命中率天然更高**：候选来自高德检索，不是模型记忆。
- **生成更快**：事实已经摆在面前，模型不必用昂贵的 reasoning 去回忆
  「苏州博物馆周一闭馆吗」——而这正是 3-5 分钟生成时长的主要来源。
- **与既有原则同源**：三态诚实（拿不到就不生成清单）、确定性优先（闭馆判定
  是规则解析不是模型判断）、体检不隐瞒（体检仍在，只是退居兜底）。

## 后果

- prompt 版本 2.1.0 → 3.0.0（语义变更）
- `Plan.grounding` 新增摘要字段（候选规模 / 避开闭馆数 / 剔除数），UI 如实展示
- 事实层**永不阻断生成**：检索失败/无覆盖 → 退回「盲写 + 体检兜底」的老路径
- 清单体积随天数增长（4 天 12 景点 + 8 餐饮；7 天 21 + 14），
  否则模型会频繁跳出清单，事实先行的收益被抵消
- 桩测试的开关词必须只从用户可控字段（目的地/偏好）取——prompt 正文里
  现在有真实营业时间原文（「全天不开放」含「空」），整条 prompt 匹配会误伤
  （见 `scripts/stub-llm.mjs` 的 `switchSource`）

## 不做什么

- **不做硬菜单**：清单是「优先选」而非「只能选」。硬菜单会让行程平庸，
  且清单召回不足时直接产出坏行程——而体检无法发现「清单外的好地方被漏掉了」。
- **不在 MOCK 模式编候选**：没有高德就没有事实，编一份假清单等于
  把「假装验真过」写进生成过程。
- **不因为读不懂就判闭馆**：营业时间解析失败一律 `unknown`，
  该地点照常进清单但不标时间（宁可少说，不能说错）。
