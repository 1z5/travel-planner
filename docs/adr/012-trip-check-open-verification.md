# ADR-012: Trip Check——把「行程可执行性核验」做成开放标准与凭据

## 状态

已接受（2026-10-28，S1 已落地）

## 背景

2026-10 全球市场重调研（`research/2026-10-global/`，结论见
[PRODUCT-REVOLUTION-2026-10.md](../PRODUCT-REVOLUTION-2026-10.md)）暴露了一个
结构性问题：产品的核心能力（事实先行 + 体检 + 修复）在上一轮定位里被包装成
**To C 功能叙事**，但市场证据指向相反的方向：

1. **生成已被商品化**：ChatGPT/Claude/OTA/地图 App 都能生成行程；腾讯地图 V11、
   飞猪帮帮、Trip.Planner、豆包都已上线。
2. **基础体检也被数据源商品化**：高德 2026 原生 15 维推演 + 闭店识别 + 改进建议；
   Ask Maps 全球铺开并可拍照纠正营业时间。L2「规则体检」不再稀缺。
3. **平台拒绝背责任**：OpenAI 关停站内结账、Google 让商家做 merchant of record、
   Claude 预订前先确认 → 责任回到供给方；而 agent 化会让错误规模化。
4. **需求侧信任缺口是结构性的**：规划采用率 50–86%，但委托率只有 6–8%；
   68% 仍信品牌；中国 86% 用过、67.5% 回 OTA 复核。
5. **同命题竞品已出现**：Tripician（live Places 验真 + 纯函数可行性引擎），窗口在关。
6. **数据合规把「事实库」堵死**：高德协议 §7.3 禁存储/缓存；Google Places/Routes
   禁止与非 Google 地图同用、仅 lat/lng 可缓存 30 天。单人团队不能做多源事实层。

## 决策

1. **形态从 To C 功能转为「可执行性核验层」**：C 端产品保留，作为展示面/试验场；
   核心资产变成**开放核验引擎 + 可对账凭据 + API/MCP 分发**。
2. **两轴报告，不做一个总分**：
   - 结构自洽性（时间轴/节奏/预算/重复/空天）→ 0–100 + A/B/C/D；
   - 事实核验（地点存在性/营业时间/路程来源与三态）→ 覆盖率 + verified/partial/unverified。
     两轴混算会把「没核验」洗成「没问题」，违反项目「不猜、不假装」的第一原则。
3. **凭据用确定性哈希，不做数字签名**：
   `id = sha256(specVersion|engineVersion|rulesetVersion|sha256(canonicalJson({document,options})))`。
   语义诚实：保证「同一输入 + 同版本引擎 → 同一结论，任何一方可复算」，不声称不可伪造。
   签名与密钥托管留到 S3（有真实买方信号后）。
4. **标准与参考实现 Apache-2.0 开源**：规则公开才能被审计、被引用、被争议；
   分发靠 `/api/verify` + `/api/mcp` + JSON Schema + schema.org JSON-LD，不靠闭源壁垒。
5. **无状态、不落库**：`POST /api/verify` 不保存输入文档；事实数据归客户/来源，
   与高德 §7.3 和 B 端「客户持数据许可」的形态相容。
6. **本轮不接支付/订阅**：App Store 规划类 2026 年负面 29% 是扣费问题；
   先验证「买方是否愿意为证据付费」（S2 三个买方问价），再投入商业化。

## 后果

- **能力复用**：`lib/executability.ts` 的扣分思想、`lib/validate.ts` 的阈值口径、
  `lib/schedule.ts`/`lib/poi-hours.ts` 的判定原语被重组成独立、可复算的引擎；
  自家行程与第三方行程走同一套规则（否则「开放标准」是假的）。
- **新增维护面**：公开 API 需要限流/CORS/限流文案/版本兼容策略；规则变更要同步
  规则集版本与文档，否则凭据对账会失效。
- **叙事风险**：MOCK/未核验期间不能对外说「真实世界核验」；必须全链暴露 `source`
  与三态。真实高德 key 验收仍是上线叙事前提（见 NEXT_STEPS）。
- **商业化前置**：高德 §3.2.1 商业目的需购买技术服务许可；现有 Plan 持久化 POI
  事实与 §7.3 冲突——收费/商用前必须解决或改为「只存引用」。
- **竞争窗口**：Tripician 已占位同一命题；本轮选择「速度 > 完整度」，先让
  可复算凭据/API/MCP 成立，再迭代规则与买方验证。

## 替代方案（为什么没选）

| 方案                               | 否决理由                                                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------------------- |
| 继续做 To C「会体检的行程规划师」  | 基础体检被数据源原生能力覆盖；C 端信任属于品牌，不属于未上线的一人项目                            |
| 全球化事实层（Google Places/OSM）  | Google 条款禁止与非 Google 地图同用 + 仅 lat/lng 可缓存 30 天；高德禁存储；多源合规债单人承担不起 |
| 纯 MCP 包装（只把已有 API 包一层） | 行业调研：58% 的 MCP 构建者只是包已有 API；无判定的包装没有差异化                                 |
| 数字签名凭据                       | 没有密钥托管与买方校验方时，签名只证明「我们签发过」，反而制造假信任                              |
| 做实时库存/预订                    | 需商户直签/渠道资质（Reserve with Google、Tiqets 200 单/月、GYG 1M visits），单人不可行           |
