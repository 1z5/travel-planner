# ADR-015: 可分享的行程体检报告工件 + 基于营业窗口的建议

## 状态

已接受（2026-10-28，S1.7）

## 背景

S1/S1.5/S1.6 把核验层做成了「判定 + 修复 + 产品内闭环」，但结论仍锁在产品页面里：

- 分享页只有一张凭据卡，工作台体检镜头要登录设备本地的链接才能打开——**证据本身不可传播**；
- 调研结论（R2）显示传播是这类产品的增长飞轮（Wanderlog/TripIt/Polarsteps 都靠「可分享工件」），
  而我们的差异化（两轴结论 + 可复算凭据）恰恰是最值得被转发的东西；
- 另一方面，判定器对「营业时间对不上」只给方向性文案（换一天/换时段），但**文档里就有当天营业
  窗口**——本可以算出「几点去是开门的」，却让用户自己去读营业时间原文。

## 决策

1. **可分享报告工件三件套**（数据同源 `lib/trip-check-report.ts`，纯函数单测覆盖）：
   - `/p/<id>/check` 公开报告页（服务端渲染、只读、无状态）：两轴结论、覆盖、分组问题
     （含规则 ID/证据/修复方向/**建议**）、凭据区、诚实声明；
   - `/p/<id>/check/poster` 竖版海报（1080×1920，`ImageResponse`，与行程海报同一套纸面语言
     与 Satori 约束）：等级/分数、facts 状态、最多 4 条阻断/微调问题、凭据 ID +「可复算·不是签名」；
   - 纯文本报告（`reportPlainText`）：微信/邮件/工单里粘贴的是人话，同时保留规则 ID 与凭据 ID。
2. **入口**：分享页凭据卡、工作台体检镜头、`/verify` 分享模式三处都能到达报告页/海报。
3. **基于营业窗口的建议**：`poi-hours` 导出 `openWindowsOnDate`（与判定同一套解析/选择逻辑，
   矛盾即 null）；引擎对 `TC-F204` 计算 `suggestion`——当天营业窗口 + 原定停留放得进哪一段
   （放不进则说「建议缩短停留或换点」）。**只建议、不修改**；闭馆日/原文读不出 → 不给建议。
4. **诚实边界**：MOCK/未核验行程的页面与海报**不得**写成「已核验」；凭据可复算但不是签名；
   报告是时点结论（凭据签发之后的变化不覆盖）。

## 后果

- **差异化变得可传播**：转发的是「这条行程被验过 + 证据 + 凭据」，不是又一份行程表——
  这正是调研里「没人产品化」的那一格。
- **行动性提升但不越界**：建议从文档自带事实算出，用户仍自己决定改不改。
- **维护面**：报告页/海报/纯文本共享同一模型，新增字段只改 `trip-check-report.ts` + 单测；
  海报受 Satori 约束（无 line-clamp、显式 flex），改海报前必读 `app/p/[id]/poster/route.tsx` 注释。
- **风险**：海报是图片，信息密度低 → 只放 TOP 问题 + 「还有 N 条」并链到完整报告页；
  未核验行程的海报可能被误读为「认证」→ facts 状态行与「不是签名」声明是必填元素。

## 替代方案（为什么没选）

| 方案           | 否决理由                                                     |
| -------------- | ------------------------------------------------------------ |
| 生成 PDF 报告  | 需要引入渲染依赖/字体；竖版海报图片已覆盖微信传播主场景      |
| 海报带二维码   | 需要二维码依赖（当前零新增依赖原则）；凭据 ID + 链接已够复算 |
| 建议直接改行程 | 违反「体检而非改写」；建议只是把文档里已有的事实算清楚       |
| 签名报告       | 无密钥托管与买方校验方（S3 再议），现在做只会制造假信任      |
