# ADR-013: Trip Check Repair——从「判定」到「确定性修复 + 前后凭据链」

## 状态

已接受（2026-10-28，S1.5 已落地）

## 背景

ADR-012 把「行程可执行性核验」做成开放标准（判定 + 可复算凭据 + API/MCP）。但 2026-10
全球调研里最硬的空白是：**错误率高，但没有人给修复闭环**。

- 356 份真实 AI 行程 telemetry：43% 的行程日至少含一个可验证错误
  （414 次提前到场 / 159 次超闭馆 / 127 次闭馆日 / 305 天绕路；厂商自述数据，量级参考）；
- 竞品与用户差评都指向同一件事：能检测，改不了 / 改完不知道有没有变好
  （TripIt 断同步、Wanderlog AI 只提建议、Tripomatic 26.6 才加强度警告）；
- 自家产品侧已有「换一个 / 一句话改 / 一键修复 / 重排」，但只服务自家行程；
  开放核验层如果只判不修，第三方拿到报告仍然要手改——「开放」就不完整。

## 决策

1. **修复器是纯函数、与引擎同源**：`lib/verify/repair.ts` 复用同一套 `verifyDocument` 做
   before/after 重验（同一个 `now`、同一口径）——「修复后变好了」不由修复器自己说。
2. **只做机械变换，且必须可枚举**：规则元信息新增 `mechanicalFix: retime | dedupe`，
   当前只标 3 条规则（TC-C102 时间重叠、TC-C103 时间接不上、TC-C109 同一天重复点位）。
   单测断言「除此之外没有任何规则可机械修复」——防止把需要取舍的问题悄悄自动化。
3. **不编造事实、不替用户取舍**：不新建地点、不改营业时间、不补路段耗时、不删独立点位、
   不改日期/预算。缺路段数据时只消除时间重叠（可达性仍由 TC-C104 如实说明）。
4. **24:00 边界整天回滚**：顺延会跨天就整天的修复作废，避免产出「24:30」这种假时刻；
   同时在 `unrepairable` 里说明原因。
5. **修复前后凭据链**：同一 `now` 下签发 `parentCredential`（修复前）与 `credential`
   （修复后）。两张凭据口径与 ADR-012 完全一致（sha256 + 规范 JSON + 引擎/规则版本），
   任何一方可分别复算；修复后文档再 `/api/verify` 必须得到同一张后凭据（部署冒烟断言）。
6. **只读不写回**：`shareId` 路径读 Plan 做修复，但 `persisted:false`，绝不改用户的行程；
   是否采纳修复文档由用户在产品里决定。
7. **诚实优于完整**：`changed=false` / `improved=false` 是合法且常见的结果（能修的都修了，
   或本来就没问题），UI/报告必须如实呈现，不把「没有机械修复」粉饰成「已优化」。

## 后果

- **闭环**：判定 → 修复 → 重验 → 前后凭据，构成对「43% 有错但没人修」的直接回应；
  第三方接入一个端点即可获得可执行版本与可对账证据。
- **护城河加深**：竞品可以抄单条规则，但抄不走「同一套确定性引擎既判又修、结果可复算、
  前后可对账」的闭环；也抄不走三态治理（miss/error/not_checked 不混用）。
- **边界清晰**：涉及内容取舍的问题（换点/删点/预算/节奏/日期/事实核验）仍归人工与产品侧，
  修复器的 `unrepairable` 清单就是「下一步该人做什么」。
- **风险**：retime 的贪心策略在极端文档（长链 + 无路段）下可能整晚；已有 24:00 回滚与
  `TC-C104` 兜底，后续如买方要求可加「拆天/删点」的显式策略（需产品决策，不默认自动化）。
- **凭据语义不变**：仍未做签名（S3 + 买方信号后再议），修复链只保证可复现/可对账。

## 替代方案（为什么没选）

| 方案                      | 否决理由                                                   |
| ------------------------- | ---------------------------------------------------------- |
| 用 LLM 自动修复           | 慢、会编、结论不可复算；与「可对账」的根本目标冲突         |
| 自动删点/换点（激进模式） | 涉及内容取舍（用户想去哪不该由引擎定）；误删会直接毁掉行程 |
| 修复结果直接写回分享行程  | 违反「体检而非改写」的产品红线；用户必须自己确认           |
| 只做产品内修复、不开放    | 放弃开放核验层的完整性；第三方仍需手改                     |
