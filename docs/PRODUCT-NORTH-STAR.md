# 产品北极星 · v5 之后的路

> 一句话定位：**不是「AI 帮你写一份行程」，而是「你的私人旅行执行官」**——
> 生成前就拿着真实世界去排，生成后还能改，出行当天照着就能走。

本文档回答两个问题：**这个产品为什么会成为伟大的产品**（而不是又一个 AI 行程生成器），
以及**下一轮该做哪一条**（四条赛道 + 判断依据）。

---

## 一、先说诊断：产品真正的资产，和它被用错了地方

这个产品最有价值的部分不是「会写行程」——那是任何人都能调到的 LLM 能力。
真正稀缺的是**真实世界的事实层**：POI 是否真实存在、几点开门、哪天闭馆、
两站之间到底要走多久。这套能力是���在真实高德 key 上、踩了几十个坑才建起来的。

但 v4 之前，这套能力**全部用在了生成之后**：

```
LLM 盲写（手上没有任何事实） → 生成完 → 高德验真 → 体检抓闭馆/绕路/时间接不上 → 用户一键修
```

体检成了生产线上的质检员：它能发现问题，不能避免问题。用户拿到的是
「AI 写的行程 + 一堆警告 + 修复按钮」，而不是「一份走得通的行程」。

**v5 的核心改动（已落地，见 [ADR-006](../docs/adr/006-ground-truth-first.md)）**：
把事实层前置——生成前先用高德检索出一份**已核验的真实素材清单**
（名称、位置、营业时间、闭馆日、评分、人均），交给模型去排。
闭馆日在源头就被排除，POI 全部来自真实检索，模型不必再靠记忆编造事实。

这一改动带来的不只是「少几条预警」，而是**产品形态的改变**：
体检从「质检员」变回「安全网」，它安静下来的那天，才是产品可信的那天。

## 二、赛道

按「**能不能形成复利**」排序。前两条是护城河，第三条是留存，第四条是付费点。

### A. 事实先行 ✅ 已落地（v5）

**做什么**：生成前取真实事实 → 注入 prompt → 行程天生可执行。

**为什么这是颠覆性**：市面上所有 AI 行程工具的共同缺陷是「闭馆日、绕路、
不存在的店」——它们靠事后体检补救，用户看到的永远是「你的行程有 7 个问题」。
事实先行让这些警告**几乎不再出现**，产品的可信度从「AI 说」变成「系统核过」。

**已交付**：`lib/grounding.ts`（清单生成）、`lib/amap.ts#searchPois`（候选检索）、
`lib/poi-hours.ts#checkDayAvailability`（当天可用性）、prompt v3.0.0、
`Plan.grounding` 摘要 + UI 徽章。

### D. 旅行档案（Travel DNA）✅ 已落地（v6.1）——产品的复利资产

**问题**：这个产品现在**不记得用户**。每份行程都从零开始：
用户第 10 次说「我不想爬山」「别给我排早八点的景点」「我住 400 块以内的酒店」，
系统还是当第一次见面。

**为什么这是护城河**：生成能力会迅速商品化，但**记忆是复利的**。
用得越久，产品越像"你的"产品，切换成本越高。竞品可以一夜之间抄掉
「事实先行」，抄不掉「知道你是个什么样的人」。

**做什么（具体到字段）**：

| 档案维度   | 形态                                 | 怎么来                      | 怎么用                            |
| ---------- | ------------------------------------ | --------------------------- | --------------------------------- |
| 体力上限   | 日步数 / 单日爬升                    | 用户显式设定 + 实际行程回填 | 体检「节奏超限」阈值按档案动态化  |
| 预算弹性   | 分类弹性系数（吃可以超，交通不能超） | 从历次改行程的倾向推断      | prompt 里给弹性区间而非一个硬总额 |
| 忌口与雷区 | 忌口 / 不接受拼团 / 不住青旅         | 显式                        | 直接进 prompt 的硬约束            |
| 作息       | 早起党 / 睡到自然醒                  | 显式 + 从生成时间轴推断     | 每天首站时间锚点                  |
| 交通耐受   | 单段最长通勤可接受分钟数             | 显式                        | 体检绕路阈值动态化                |
| 踩过的坑   | 「上次这家太远了」「这家排队久」     | 行中模式的一键反馈          | 后续同类候选降权                  |

**飞轮**：`规划 → 执行（行中模式）→ 一键反馈（太满/太远/别去这家）→ 档案更新 → 下一份更准`

**关键实现约束（必须诚实）**：

- 档案**冷启动**要靠显式滑杆（一次性 30 秒），不能等系统"自己学会"；
- 每条档案都要能**溯源与手改**（"这条是你上次反馈的，删掉？"）——
  黑箱画像比没有画像更让人不安；
- 推断出来的偏好要**标注为推断**（「根据你上次的行程推测」），与用户明示的分开；
- 未登录用户也能有档案（存本地），登录后才跨设备。

**为什么适合 OPC**：纯增量、可自服务、零运营负担、随使用变厚。

**已交付（v6.1）**：`lib/profile.ts`（五字段 + 推断治理类型与 UI 契约）、`lib/profile-store.ts`（localStorage）、`lib/planner.ts` 档案行注入（三路径共用读取点）、`lib/validate.ts` 节奏阈值按 stamina 动态化、`components/ProfileDrawer.tsx`（30 秒冷启动 + 每条可改可删）、`app/api/plan` profile 字段校验与透传。三条红线：零变化（无档案时逐字一致，负向断言守卫）、推断必标注可删、**v1 不做推断引擎**（治理契约先做实）。

### B. 传播飞轮：行程即内容 ✅ 已落地（v6）

**做什么**：海报级分享页（`PosterCover`：值得截图的封面 + 动态 OG）+ 一键克隆
（`POST /api/plan/clone`：继承原 input、覆盖档期/预算/节奏，走完整生成管线——
事实层对新日期重新核验闭馆与通勤）+ 旅程报告（`/r/<token>`：post-trip 海报）。

**为什么这是颠覆性**：市面上的 AI 行程工具全是「用完即走的生成器」，分享链接是一张
没人会打开的表格。传播飞轮把每一条分享链接变成新用户的起点（克隆），把出行结束变成
第二轮传播（报告）。竞品可以抄海报的皮，抄不走「克隆即适配」——那需要同款事实层。

**已交付**：`components/PosterCover.tsx`、`components/CloneCTA.tsx`、`lib/plan-clone.ts`、
`app/api/plan/clone/`、`lib/trip-report.ts`、`app/r/[id]/`、`components/TripReport.tsx`、
`app/p/[id]/opengraph-image.tsx`。诚实红线：海报缺数据整块不渲染；报告无行中确认数据
就绝不声称「打卡」（负向断言守卫）；克隆必须走完整管线（不做复制 JSON 的假克隆）。

### C. 行中重规划求解器 ✅ 已落地（v6）

**问题**：现在的行中模式只**展示**今天的安排。现实是：现在 15:30，你在一个点，
突然下雨，19:00 有个不能改的活动，剩下的三个点里有两个要开 40 分钟车。
用户需要的是「接下来怎么走」——这是**约束求解**，不是生成。

**做什么**：`/api/plan/replan`（确定性、毫秒级、不调模型）：
输入 = 当前时刻 + 当前位置 + 今天剩余行程点 + 真实路段耗时 + 各点营业时间 + 固定活动；
输出 = 可行的子序列（顺序 + 新时刻）+ **明确说明放弃了什么、为什么**。

```
现在 15:30 · 你在 拙政园
✅ 16:10-17:00  平江路（步行 22 分钟）
❌ 放弃 苏州博物馆 —— 16:00 闭馆，到不了
❌ 放弃 诚品书店 —— 17:00 后还有 40 分钟车程，赶不上 19:00 的活动
```

**为什么确定性**：这是约束满足问题（时间窗 + 旅行时间 + 固定锚点），
LLM 解它又慢又会编（「你可以在路上顺便看看」这种话没有约束力）。
本项目已有 `lib/schedule.ts` 的冲突检测与顺延，扩展成求解器是同一条路。

**为什么留存**：出行的真实价值在当天。**行中模式用得好 = 产品被用得久**，
这直接决定这是不是一个能收费的产品。

**已交付（v6）**：`lib/replan.ts`（client-safe 确定性求解器：固定活动锚点 + 营业时间 +
真实路段，放弃必给引用真实数据的理由）+ `app/api/plan/replan/`（毫秒级、不调模型、
不扣配额、不落库）+ TodayView「接下来怎么走」面板（建议不自动执行）。无真实路段 →
422 诚实降级。

**风险**：需要真实路段数据（境外无覆盖 → 诚实降级）；求解器要给"放弃"的理由，
理由必须来自真实约束，不能是模型编的。

### E. 出行准备包 ✅ 已落地（v8.1）——付费与传播的抓手

**问题**：行程只解决「到了当地怎么走」，没解决「出发前要准备什么」。
而这恰恰是中国用户最痛的一段：**门票预约**（故宫、国博要提前几天、几点放票）、
**打包清单**（雨伞/防晒/登山鞋/充电宝/常备药）、**证件与交通**（身份证/预约码/接驳车）。

**做什么**（按可做性排序）：

1. **打包清单（确定性，无外部依赖）**：由行程内容（户外/登山/海边/夜市）+ 天气 +
   天数推导，逐条给出理由（「3 天里有 1 天爬山 → 抓地运动鞋」）。这是免费的、立刻能做的。
2. **预约日历（需要数据源，维护成本高）**：头部场馆的预约规则做人工策展库，
   **每条都带「以官方公告为准」+ 更新时间**——这是数据维护生意，不是技术活，
   一个人做要克制规模（Top 50 足够覆盖大多数行程）。
3. **证件/交通清单**：从必游地类型推导（「博物馆」→ 身份证；「需要预约的场馆」→ 预约码）。

**为什么付费**：这是唯一一个「出发前 48 小时，用户愿意付钱」的场景。

---

### F. 多人共编 + AA 分账 —— 除非有人搭把手，否则不做

**为什么诱人**：旅行本来就是一群人的事；共编（投票、分账）是所有工具都没做好的地方。
**为什么现在不做**：需要实时同步、冲突仲裁、滥用治理——这是「产品之外的运维」，
一个人做会把它做成一个半成品。**除非有第二个人的带宽，否则不做。**
（真要做，先做最笨的版本：链接共享 + 各自提 spots + 一次性出合并方案。）

## 三、北极星指标

> **「照着走完」的比例** = 用户出行期间未手动改过当天安排的行程占比。

这个指标比「生成了多少份行程」诚实得多：生成量衡量的是获客，
「照着走完」衡量的是**产品有没有真的帮上忙**。

配套观察：闭馆/绕路预警率（应持续下降）、行中模式使用率（留存）、
二次生成间隔（越短说明档案/记忆越有效）。

## 四、决策记录

| 决策                                 | 理由                                               |
| ------------------------------------ | -------------------------------------------------- |
| 事实先行做在**生成前**而不是体检加强 | 体检只能发现问题；事实先行能避免问题（见 ADR-006） |
| 清单是「优先选」不是「只能选」       | 硬菜单会让行程平庸，且清单召回不足时直接产出坏行程 |
| 档案可以本地存、不强制登录           | 陌生人可用的前提是「不用注册就能用」；登录只换同步 |
| 行中重规划用求解器不用 LLM           | 约束满足要确定性、要毫秒、要能解释「为什么放弃」   |
| 共编/交易层暂不做                    | OPC 的带宽要花在复利资产上，不是运维上             |

### 切片 1 · 旅行档案（Travel DNA）✅ 已落地（v6.1）

**要碰的文件**：

- 新增 `lib/profile.ts`（**client-safe 纯函数**，与 `lib/budget.ts` 同风格）：`TravelProfile` 类型、默认值、字段校验、从 `PlanInput` 推导初始档案、`renderProfileLines(profile)`（渲染成 prompt 行，给 `lib/planner.ts` 的 `baseLines` 用）
- 新增 `lib/profile-store.ts`：**先做 localStorage 版**（照抄 `lib/recent-trips.ts` 的模式），登录后再谈服务端同步。别一上来就动 `lib/store/` 四个接口 + Prisma schema——那是 v3 级别的大工程，会把这条赛道拖成一个季度
- 改 `lib/planner.ts`：`baseLines()` 追加档案行（体力上限 / 忌口 / 作息 / 交通耐受）
- 改 `lib/validate.ts`：**只先做一处动态化**——日净游玩时长上限按档案的体力上限调整（现阈值 10 小时，档案说「日行 1.2 万步」就降到 8 小时），其余阈值先不动
- 改 `app/home-client.tsx` + `components/`：加「我的档案」抽屉（首次进入引导 30 秒）

**验收标准**：

1. 档案能存、能读、能改、能删；未登录也能用（localStorage）
2. 生成时 prompt 里含档案行（e2e 用桩断言：档案开关词 → 桩校验 prompt 含档案）
3. 体检的节奏上限随档案变化（同一份行程，档案「轻松」vs「紧凑」预警不同）
4. 每条**推断出来的**偏好都标注为推断，且能溯源（「根据你上次的行程推测」）

**最容易踩的坑**：

- ❌ 把档案做成黑箱画像 → 用户不安、要求删不掉。**每条都要能手改、能溯源**
- ❌ 冷启动靠「系统自己学会」 → 用户不会等。要有 30 秒显式引导
- ❌ 档案字段一次性设计 20 个 → 没人填。先 5 个字段跑通飞轮

### 切片 2 · 行中重规划求解器 ✅ 已落地（v6）

**要碰的文件**：

- 新增 `lib/replan.ts`（**client-safe 纯函数求解器**，扩展 `lib/schedule.ts` 的能力）：

  ```
  输入：now（当天分钟数）+ 当前位置 + 剩余行程点（含 time/durationMin）
        + 真实路段（day.legs）+ 各点营业时间（spot.poi）+ 固定锚点（用户活动）
  输出：{ kept: 行程点[], dropped: {name, reason}[], timeline: 新时刻[] }
  ```

  求解逻辑：固定锚点当不可移动的墙 → 锚点之前的点按「剩余时间够不够 + 营业时间开不开门」贪心保留 → 每个被丢弃的点必须给出**来自真实约束的理由**（「16:00 闭馆，到不了」/「17:00 后还有 40 分钟车程，赶不上 19:00 活动」）

- 新增 `app/api/plan/replan/route.ts`：`POST { shareId, now? }` → 读 Plan → 求解 → 返回。**默认不落库**（用户可能试几次），用户明确选了某个方案时再落库带 revision
- 改 `components/TodayView.tsx`：加「重新安排接下来」按钮 + 结果区（保留的 / 放弃的）

**验收标准**：

1. 给定「现在 15:30 + 剩余 3 个点 + 真实路段 + 19:00 固定活动」，输出一个**可行**子序列（不出现「时间接不上」）
2. 每个被放弃的点都有理由，且理由**引用真实数据**（闭馆时间 / 路程时长），不是模型编的措辞
3. 毫秒级返回、不调模型、不扣配额（照 `api/plan/adjust` 的契约来）
4. 没有真实路段（境外 / 高德波动）→ 诚实降级：「缺少真实路程，无法重排」

**最容易踩的坑**：

- ❌ 用 LLM 重排 → 又慢又编，且解释不可信。这个问题的本质是约束满足
- ❌ 悄悄把用户改过的点删掉 → 放弃必须**显式列出**且不自动落库
- ❌ 忘了「今天已经走过的点」 → 只能对**未来**的点重排

### 切片 3 · 出行准备包——第一个提交

**要碰的文件**：

- 新增 `lib/packing.ts`（**client-safe 纯函数**）：`(plan, weather?) → PackingItem[]`，每项 = `{ label, reason, source }`，`source` 必填（来自行程的哪个点 / 哪天的天气）。推导规则示例：室外景点 → 防晒 / 遮阳帽；雨天 → 雨具；爬山 / 台阶 → 抓地运动鞋；夜市 / 夜游 → 充电宝（导航耗电）；连续 3 天以上 → 常用药 / 换洗衣物
- 改 `components/PlanView.tsx` + `components/TodayView.tsx`：加「出发前准备」卡

**验收标准**：

1. 每一项都能点开看到**依据**（「第 2 天有 1 个室外景点」→ 防晒）
2. 没有依据的项**不出现**（不猜、不塞通用清单凑数）
3. 天气未知时降级为「仅按行程推导」，并说明「含雨具建议，需联网查天气」

**最容易踩的坑**：

- ❌ 输出通用打包清单（「换洗内衣、充电器」）→ 没有信息量，用户不看第二遍
- ❌ 预约规则自己编 → 预约数据要么接官方源，要么人工策展并**标日期 +「以官方公告为准」**，不要让模型凭记忆生成「故宫提前 7 天 20:00 放票」这种易错信息

### 三条赛道的共同验收口径

- 不许破坏既有能力：`npm run typecheck && npm run lint && npm run test:unit && npm test` 全绿
- 诚实优先于丰富：拿不到就明说「没有」，不用默认值填充
- 每条赛道都要有**故障路径**的测试（不只是 happy path）
