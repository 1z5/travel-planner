# 产品北极星 · v5 之后的路

> 一句话定位：**不是「AI 帮你写一份行程」，而是「你的私人旅行执行官」**——
> 生成前就拿着真实世界去排，生成后还能改，出行当天照着就能走。

本文档回答两个问题：**这个产品为什么会成为伟大的产品**（而不是又一个 AI 行程生成器），
以及**下一轮该做哪一条**（四条赛道 + 判断依据）。

---

## 一、先说诊断：产品真正的资产，和它被用错了地方

这个产品最有价值的部分不是「会写行程」——那是任何人都能调到的 LLM 能力。
真正稀缺的是**真实世界的事实层**：POI 是否真实存在、几点开门、哪天闭馆、
两站之间到底要走多久。这套能力是���在真实高德 key 上、踩了几十个坑才建起来的。

但 v4 之前，这套能力**全部用在了生成之后**：

```
LLM 盲写（手上没有任何事实） → 生成完 → 高德验真 → 体检抓闭馆/绕路/时间接不上 → 用户一键修
```

体检成了生产线上的质检员：它能发现问题，不能避免问题。用户拿到的是
「AI 写的行程 + 一堆警告 + 修复按钮」，而不是「一份走得通的行程」。

**v5 的核心改动（已落地，见 [ADR-006](../docs/adr/006-ground-truth-first.md)）**：
把事实层前置——生成前先用高德检索出一份**已核验的真实素材清单**
（名称、位置、营业时间、闭馆日、评分、人均），交给模型去排。
闭馆日在源头就被排除，POI 全部来自真实检索，模型不必再靠记忆编造事实。

这一改动带来的不只是「少几条预警」，而是**产品形态的改变**：
体检从「质检员」变回「安全网」，它安静下来的那天，才是产品可信的那天。

## 二、四条赛道

按「**能不能一个人做出来 + 能不能形成复利**」排序。前两条是护城河，第三条是留存，
第四条是付费点。

### A. 事实先行 ✅ 已落地（v5）

**做什么**：生成前取真实事实 → 注入 prompt → 行程天生可执行。

**为什么这是颠覆性**：市面上所有 AI 行程工具的共同缺陷是「闭馆日、绕路、
不存在的店」——它们靠事后体检补救，用户看到的永远是「你的行程有 7 个问题」。
事实先行让这些警告**几乎不再出现**，产品的可信度从「AI 说」变成「系统核过」。

**已交付**：`lib/grounding.ts`（清单生成）、`lib/amap.ts#searchPois`（候选检索）、
`lib/poi-hours.ts#checkDayAvailability`（当天可用性）、prompt v3.0.0、
`Plan.grounding` 摘要 + UI 徽章。

---

### B. 旅行档案（Travel DNA）——产品的复利资产 ⭐ 下一轮首选

**问题**：这个产品现在**不记得用户**。每份行程都从零开始：
用户第 10 次说「我不想爬山」「别给我排早八点的景点」「我住 400 块以内的酒店」，
系统还是当第一次见面。

**为什么这是护城河**：生成能力会迅速商品化，但**记忆是复利的**。
用得越久，产品越像"你的"产品，切换成本越高。竞品可以一夜之间抄掉
「事实先行」，抄不掉「知道你是个什么样的人」。

**做什么（具体到字段）**：

| 档案维度   | 形态                                 | 怎么来                      | 怎么用                            |
| ---------- | ------------------------------------ | --------------------------- | --------------------------------- |
| 体力上限   | 日步数 / 单日爬升                    | 用户显式设定 + 实际行程回填 | 体检「节奏超限」阈值按档案动态化  |
| 预算弹性   | 分类弹性系数（吃可以超，交通不能超） | 从历次改行程的倾向推断      | prompt 里给弹性区间而非一个硬总额 |
| 忌口与雷区 | 忌口 / 不接受拼团 / 不住青旅         | 显式                        | 直接进 prompt 的硬约束            |
| 作息       | 早起党 / 睡到自然醒                  | 显式 + 从生成时间轴推断     | 每天首站时间锚点                  |
| 交通耐受   | 单段最长通勤可接受分钟数             | 显式                        | 体检绕路阈值动态化                |
| 踩过的坑   | 「上次这家太远了」「这家排队久」     | 行中模式的一键反馈          | 后续同类候选降权                  |

**飞轮**：`规划 → 执行（行中模式）→ 一键反馈（太满/太远/别去这家）→ 档案更新 → 下一份更准`

**关键实现约束（必须诚实）**：

- 档案**冷启动**要靠显式滑杆（一次性 30 秒），不能等系统"自己学会"；
- 每条档案都要能**溯源与手改**（"这条是你上次反馈的，删掉？"）——
  黑箱画像比没有画像更让人不安；
- 推断出来的偏好要**标注为推断**（「根据你上次的行程推测」），与用户明示的分开；
- 未登录用户也能有档案（存本地），登录后才跨设备。

**为什么适合 OPC**：纯增量、可自服务、零运营负担、随使用变厚。

### C. 行中重规划求解器——从「能看」到「能用」

**问题**：现在的行中模式只**展示**今天的安排。现实是：现在 15:30，你在一个点，
突然下雨，19:00 有个不能改的活动，剩下的三个点里有两个要开 40 分钟车。
用户需要的是「接下来怎么走」——这是**约束求解**，不是生成。

**做什么**：`/api/plan/replan`（确定性、毫秒级、不调模型）：
输入 = 当前时刻 + 当前位置 + 今天剩余行程点 + 真实路段耗时 + 各点营业时间 + 固定活动；
输出 = 可行的子序列（顺序 + 新时刻）+ **明确说明放弃了什么、为什么**。

```
现在 15:30 · 你在 拙政园
✅ 16:10-17:00  平江路（步行 22 分钟）
❌ 放弃 苏州博物馆 —— 16:00 闭馆，到不了
❌ 放弃 诚品书店 —— 17:00 后还有 40 分钟车程，赶不上 19:00 的活动
```

**为什么确定性**：这是约束满足问题（时间窗 + 旅行时间 + 固定锚点），
LLM 解它又慢又会编（「你可以在路上顺便看看」这种话没有约束力）。
本项目已有 `lib/schedule.ts` 的冲突检测与顺延，扩展成求解器是同一条路。

**为什么留存**：出行的真实价值在当天。**行中模式用得好 = 产品被用得久**，
这直接决定这是不是一个能收费的产品。

**风险**：需要真实路段数据（境外无覆盖 → 诚实降级）；求解器要给"放弃"的理由，
理由必须来自真实约束，不能是模型编的。

### D. 出行准备包——付费与传播的抓手

**问题**：行程只解决「到了当地怎么走」，没解决「出发前要准备什么」。
而这恰恰是中国用户最痛的一段：**门票预约**（故宫、国博要提前几天、几点放票）、
**打包清单**（雨伞/防晒/登山鞋/充电宝/常备药）、**证件与交通**（身份证/预约码/接驳车）。

**做什么**（按可做性排序）：

1. **打包清单（确定性，无外部依赖）**：由行程内容（户外/登山/海边/夜市）+ 天气 +
   天数推导，逐条给出理由（「3 天里有 1 天爬山 → 抓地运动鞋」）。这是免费的、立刻能做的。
2. **预约日历（需要数据源，维护成本高）**：头部场馆的预约规则做人工策展库，
   **每条都带「以官方公告为准」+ 更新时间**——这是数据维护生意，不是技术活，
   一个人做要克制规模（Top 50 足够覆盖大多数行程）。
3. **证件/交通清单**：从必游地类型推导（「博物馆」→ 身份证；「需要预约的场馆」→ 预约码）。

**为什么付费**：这是唯一一个「出发前 48 小时，用户愿意付钱」的场景。

---

### E. 多人共编 + AA 分账 —— 除非有人搭把手，否则不做

**为什么诱人**：旅行本来就是一群人的事；共编（投票、分账）是所有工具都没做好的地方。
**为什么现在不做**：需要实时同步、冲突仲裁、滥用治理——这是「产品之外的运维」，
一个人做会把它做成一个半成品。**除非有第二个人的带宽，否则不做。**
（真要做，先做最笨的版本：链接共享 + 各自提 spots + 一次性出合并方案。）

## 三、北极星指标

> **「照着走完」的比例** = 用户出行期间未手动改过当天安排的行程占比。

这个指标比「生成了多少份行程」诚实得多：生成量衡量的是获客，
「照着走完」衡量的是**产品有没有真的帮上忙**。

配套观察：闭馆/绕路预警率（应持续下降）、行中模式使用率（留存）、
二次生成间隔（越短说明档案/记忆越有效）。

## 四、决策记录

| 决策                                 | 理由                                               |
| ------------------------------------ | -------------------------------------------------- |
| 事实先行做在**生成前**而不是体检加强 | 体检只能发现问题；事实先行能避免问题（见 ADR-006） |
| 清单是「优先选」不是「只能选」       | 硬菜单会让行程平庸，且清单召回不足时直接产出坏行程 |
| 档案可以本地存、不强制登录           | 陌生人可用的前提是「不用注册就能用」；登录只换同步 |
| 行中重规划用求解器不用 LLM           | 约束满足要确定性、要毫秒、要能解释「为什么放弃」   |
| 共编/交易层暂不做                    | OPC 的带宽要花在复利资产上，不是运维上             |
